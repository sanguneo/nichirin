# 기여 규칙

`kanao-cli`는 Windows용이고 `../kakaoread-mac`의 `kamado-cli`는 macOS용
형제 구현이다. 사용자에게 보이는 의미를 함께 관리하되 플랫폼 내부를 억지로
같게 만들지 않는다. 작업 전 [AGENTS.md](AGENTS.md)를 읽는다.
현재 검토와 수정 우선순위는 [improvement.md](improvement.md)에 있다.

## 범위와 근거

- 검토·계획 요청은 제품 코드 변경 허가가 아니다. 요청한 산출물만 작성한다.
- 문제마다 현재 동작, 기대 동작, `파일:줄`, 반례, 영향, 수정 범위와 합격 기준을 적는다.
  직접 재현, 소스상 도출, 플랫폼에서 확인할 가설을 구분한다.
- 성능 주장은 입력 크기와 측정 환경을 함께 적는다. 계산한 대기 시간·복잡도를
  실측값으로 표현하지 않는다. 캐시 보유량과 프로세스 피크 메모리는 별도로 다룬다.
- 기존의 의도적인 한계는 새 결함으로 재등록하지 않는다. 계약을 바꾸는 제안은
  구현 버그와 구별하고 소비자·형제 저장소의 영향까지 적는다.

## 코드와 데이터

- 표준 라이브러리와 기존 모듈 경계를 유지한다. 변경에 필요하지 않은 추상화,
  공용 패키지, 의존성, 정리 작업을 같이 넣지 않는다.
- 실제 대화, 이름, 전화번호, 계정 경로, 키, 토큰을 fixture·로그·스크린샷·PR에
  넣지 않는다. 재현은 합성 데이터를 쓴다.
- 모든 경계 ID는 string, 메시지는 방별 log ID 순서, 모호한 대상은 후보와 함께
  거절하는 계약을 유지한다. nickname을 계정 식별자로 쓰지 않는다.
- 스냅샷 버전과 실제 읽은 내용, 실패 후 재시도, cache 소유권, 사용 중인 연결의
  수명을 함께 설계한다. 새 메시지가 아닌 기존 행의 변경도 캐시 모델에 포함한다.
- 요청하지 않은 방을 열거나 메시지를 보내지 않는다. 실전 전송은 승인된 대상과
  문구로만 수행하고, uncertain send는 자동 재시도하지 않는다.
  `submitted`를 배달 완료로 보고하지 않는다.

## 검증은 변경에 비례하게

문서·검토만 바뀌면 링크·참조·diff를 확인한다. 문구를 고정하는 테스트는 만들지
않고 전체 suite나 실제 카톡 실행을 기본으로 요구하지 않는다.
사용자가 최소 검증을 요청한 경우 그 범위를 지키고 확인하지 않은 부분을 적는다.

동작을 수정할 때는 기존 테스트를 먼저 읽고, 실제로 회귀를 잡는 작은 사례를
그 테스트 옆에 둔다. 실패를 지우거나 skip으로 바꿔 통과시키지 않는다.
예를 들어 관련 부분만 실행할 때:

```powershell
python -m unittest tests.test_snapshot tests.test_watch
```

교차 영역 변경을 통합할 때 전체 suite 명령은 다음과 같다.
빌드·설치 변경은 해당 경계의 확인도 추가하며, 플랫폼 검증을 실행하지
못했다면 생략 이유를 기록한다.

```powershell
python -m unittest discover -t . -s tests
```

- sleep과 타이밍 운에 의존하지 않는다. 시계·파일 버전·실패 순서는 주입하고,
  비동기 검증은 사건을 기다릴 준비를 먼저 한 뒤 동작을 시작한다.
- stub은 실제 오류 타입과 수명·스레드 경계를 보존해야 한다.
- CNG/Win32/console이 필요한 테스트만 명시적으로 플랫폼 guard를 사용한다.
  Windows에서 예상 밖의 skip은 조사한다. Mac에서 skip된 검증을 통과한 것으로
  보고하지 않는다.
- 실사용 확인은 변경된 동작에 한정한다. 전체 대화 수집이나 광범위한 GUI 조작으로
  작은 변경을 검증하지 않는다.

## 형제 저장소와 계약

이식에는 원본·대상 revision, 플랫폼 전제, 가져온 내용, 가져오지 않은 이유,
공통 회귀 사례를 적는다. 같은 파일명이 같은 최신 구현이라는 보장은 없다.
WAL generation과 캐시 버전, SSE cursor, 에러·ID·생략 필드 등은 공통 의미를
검사하고 CNG/Win32와 CommonCrypto/AX는 각 플랫폼에서 확인한다.

`openapi.json`을 공통 계약으로 유지하려면 양쪽 파일 존재와 적용 버전부터
확인한다. byte equality만으로 handler/backend 호환성을 보장했다고 말하지 않는다.
특히 queue 이식은 간격·실패·종료 응답·cache 소유권까지 함께 가져온다.

## 커밋과 PR

- 사용자가 요청한 경우에만 커밋·푸시한다. 기존의 다른 변경을 stage하지 않는다.
  경로를 지정해 stage하고 staged diff를 읽는다.
- 독립적으로 검토·되돌릴 수 있는 변경 단위로 커밋하고 최근 저장소의 메시지
  형식을 따른다. 관련 회귀 테스트는 해당 구현과 같이 둔다.
- PR에는 목적, 전후 동작, 불변식, 영향받는 플랫폼, 수행한 명령과 결과,
  수행하지 않은 검증과 이유를 적는다. 근거 없는 “테스트 완료”는 쓰지 않는다.
- 여러 의존 PR은 오래된 것부터 병합한다. 충돌 해결은 순서를 바꿔 숨기지 않는다.
  공유 브랜치의 history rewrite나 강제 푸시는 별도 명시적 요청 없이 하지 않는다.
- 버전·릴리스·태그는 요청 범위에 있을 때만 변경한다.
